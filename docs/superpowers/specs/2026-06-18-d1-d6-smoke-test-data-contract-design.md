# D1-D6 Smoke-Test Data Contract Design

> Status: draft for review
> Scope: module-level design for D1-D6 preprocessing, schema, split/filter contracts, KNN/RFE forbidden columns, and smoke-test acceptance.
> Out of scope for phase 1: formal runner expansion for full paper experiments.

## Goal

Build a stable D1-D6 data integration contract that makes every dataset available through offline preprocessed artifacts, a shared internal schema, configuration-driven source/target splitting, configuration-driven information sharing filters, shared KNN/RFE forbidden-column enforcement, and a smoke-test loop that proves the new path works before touching the formal experiment runner.

## Current Context

The formal experiment path currently imports root-level modules first:

- `dataset_registry.py`
- `data_preprocessing.py`
- `source_selector.py`
- `msml_tl_rfe.py`
- `experiment_runner.py`
- `scripts/run_full_paper_experiments.py`

The `src/` tree mirrors parts of this logic but is not the active main path for the paper runner. Phase 1 treats the root-level path as canonical and does not edit the `src/` mirror except where a smoke test explicitly imports it by mistake and needs to be corrected.

D1-D3 already work through dataset-specific loader branches. D4-D6 are profiled and audited but not registered in the formal training registry. The existing plan should therefore be split around contracts and testable boundaries, not around a direct runner extension.

## Approach Options

### Option 1: Patch Existing Branches In Place

Add D4-D6 as more `if/elif` branches in `load_dataset()`, `_resolve_dataset_feature_cols()`, and information sharing filters.

Pros: fastest initial edit, low file count.

Cons: repeats the D1-D3 hardcoding pattern, makes schema drift likely, and does not solve KNN/RFE forbidden-column consistency.

### Option 2: Configuration-Driven Contract Layer

Add a dataset config layer and keep preprocessing, schema validation, splitting, information sharing, feature filtering, and smoke testing behind explicit contracts.

Pros: best fit for D1-D6 differences, makes forbidden columns auditable, keeps phase 1 smoke-testable without formal runner expansion.

Cons: more upfront structure and more focused tests.

### Option 3: Full Runner Integration Immediately

Build preprocessing, schema, smoke tests, and `run_full_paper_experiments.py --include-extended-datasets` in one pass.

Pros: reaches the final user-facing command sooner.

Cons: larger blast radius; failures in full training can hide schema/preprocessing errors; harder to isolate data-contract regressions.

Recommended approach: Option 2 for phase 1. It gives a closed smoke-test loop and leaves runner expansion as phase 2 after data contracts are stable.

## Phase 1 Boundary

Phase 1 is complete when:

1. D1-D6 preprocessed artifacts exist or can be generated by deterministic scripts.
2. Each artifact satisfies the shared internal schema.
3. Each dataset has a dataset config describing paths, schema fields, split protocol, domain filters, feature candidates, and forbidden columns.
4. Source/target split works for each dataset.
5. Information sharing filtering works for each dataset under configured `domain_col`.
6. KNN and RFE candidates exclude forbidden columns.
7. A D1-D6 smoke test runs end to end on small samples and writes a pass/fail report.

Phase 1 does not add D4-D6 to the formal full experiment runner. That is a separate phase after smoke tests pass.

## Module Design

### Module A: Offline Preprocessing Artifacts

Responsibility: generate stable files in `data/preprocessed/` so experiment runs no longer redo cleaning logic.

Each preprocessing script must be deterministic, must write a summary report, and must fail on contract-breaking data quality issues instead of silently guessing.

Required artifacts:

| Dataset | Artifact | Extra artifact | Target role rule |
| --- | --- | --- | --- |
| D1 | `data/preprocessed/d1_preprocessed.parquet` | none | `entity_id=1, item_id=10` |
| D2 | `data/preprocessed/d2_preprocessed.parquet` | none | `entity_id="B1", item_id=10` |
| D3 | `data/preprocessed/d3_preprocessed.parquet` | none | `store_id=10` |
| D4 | `data/preprocessed/d4_preprocessed.parquet` | none | cold-start targets that support the `15/15/180` target protocol |
| D5 | `data/preprocessed/d5_preprocessed.parquet` | none | cold-start targets that support the `15/15/180` target protocol |
| D6 | `data/preprocessed/d6_preprocessed.parquet` | `data/preprocessed/d6_coldstart_target_ids.csv` | sampled target IDs truncated to last 210 days |

Preprocessing outputs must include:

- `date`
- `sales`
- `series_id`
- `is_target_entity`
- the dataset-specific raw entity columns needed for auditing
- configured `domain_col` values
- configured dynamic/static candidate features

Preprocessing outputs must not drop raw ID columns just because they are forbidden for modeling. The forbidden-column layer, not the preprocessing layer, decides what can enter KNN/RFE/model inputs.

### Module A0: D1-D3 Preprocessing Freeze

D1-D3 preprocessing should call the existing standardizers and add only contract columns:

- D1: `series_id = "{store}::{item}"`; target is `entity_id=1, item_id=10`.
- D2: `series_id = "{entity_id}::{item_id}"`; target is `entity_id="B1", item_id=10`; keep `entity_id_code` and `brand_code` for audit but forbid them downstream.
- D3: `series_id = "{store_id}::{item_id}"`; target is `store_id=10`; preserve `region_id="TODO_REGION_UNAVAILABLE"` when no metadata exists.

D1-D3 artifact validation must compare a sampled output against the current loader output and require `sales` mean drift below `0.01%`.

### Module A1-A3: D4-D6 Preprocessing

D4 output rules:

- source raw table: `data/train.parquet`
- target column: `sale_amount -> sales`
- entity: `series_id = "{store_id}::{product_id}"`
- domain: `city_id`
- hourly arrays expanded before writing:
  - `hours_sale_sum`
  - `hours_sale_max`
  - `hours_sale_nonzero`
  - `hours_stock_nonzero`
- validation: Pearson correlation between `hours_sale_sum` and `sale_amount` must be greater than `0.95`.

D5 output rules:

- source raw table: `train.csv`
- target column: `unit_sales -> sales`
- entity: `series_id = "{store_nbr}::{item_nbr}"`
- domain: `item_family`
- `unit_sales` values are clipped at lower bound `0`.
- `is_extreme_return_item=1` for item `759657` and `1464093`; `0` otherwise.
- join metadata from:
  - `stores.csv`: `store_city`, `store_state`, `store_type`, `store_cluster`
  - `items.csv`: `item_family`, `item_class`, `item_perishable`
  - `oil.csv`: `oil_price_lag1`
  - `holidays_events.csv`: `is_holiday`, `holiday_type`
- missing store-item-date combinations are filled with `sales=0` and `onpromotion=False`.

D6 output rules:

- source raw table: `sales_train_evaluation.csv`
- target columns: `d_1...d_1941 -> sales` after melt
- entity: `series_id = "{store_id}::{item_id}"`
- domain: `dept_id`
- join `calendar.csv` for `date`, calendar fields, event flags, and SNAP flags.
- join `sell_prices.csv` for `sell_price`.
- write `d6_subset_full.parquet` before cold-start truncation.
- write `d6_preprocessed.parquet` after target truncation.
- write `d6_coldstart_target_ids.csv` and verify it matches `is_target_entity`.

## Shared Internal Schema

Every preprocessed artifact must satisfy this required schema:

| Column | Type expectation | Rule |
| --- | --- | --- |
| `date` | datetime-compatible | non-null after parsing |
| `sales` | numeric | non-null for modeled rows; no negative values after preprocessing |
| `series_id` | string | non-null; identifies a time series and may repeat across dates |
| `is_target_entity` | integer or boolean | exactly `0/1` semantics |

Recommended compatibility columns:

- `entity_id`
- `item_id`

These may be retained for legacy functions, but phase 1 should use `series_id` as the canonical grouping key for D1-D6 smoke tests. Where legacy functions still require `entity_id/item_id`, adapters may map:

- D1: `entity_id=store`, `item_id=item`
- D2: `entity_id=brand/entity_id`, `item_id=item_id`
- D3: `entity_id=store_id`, `item_id=item_id`
- D4: `entity_id=store_id`, `item_id=product_id`
- D5: `entity_id=store_nbr`, `item_id=item_nbr`
- D6: `entity_id=store_id`, `item_id=item_id`

`series_id` remains the source of truth.

## Dataset Config Contract

Add a configuration object per dataset. It may live in `dataset_registry.py` initially or in a new root-level module such as `dataset_config.py`, but the smoke test must import one canonical source.

Each config must define:

- `dataset_name`
- `preprocessed_data_path`
- `date_col`
- `target_col`
- `series_id_col`
- `series_group_cols`
- `domain_col`
- `domain_col_fallback`
- `source_filter`
- `target_filter`
- `dynamic_feature_cols`
- `static_feature_cols`
- `knn_candidate_cols`
- `rfe_candidate_cols`
- `rfe_always_keep_cols`
- `forbidden_feature_cols`
- `split_protocol`
- `knn_matching_protocol`

Shared target cold-start protocol:

```python
{
    "target_train_days": 15,
    "target_val_days": 15,
    "target_test_days": 180,
}
```

The `15/15/180` protocol applies only to the target domain:

- target entities require `target_train_days + target_val_days + target_test_days = 210` days, split as 15 days target train, 15 days target validation, and the following 180 days forecast/test horizon.
- the target observed window is exactly the first 30 days of the target split: 15 train days plus 15 validation days.
- D6 target entities are truncated offline to the 210-day target window, so the artifact should contain exactly the target protocol window for those target IDs.

Source split is a separate long-history protocol. It must never reuse the target `15/15/180` cold-start split. For D1-D3, the paper source split is fixed by Table 3:

| Dataset | Source train | Source validation | Source test | Source split mode |
| --- | ---: | ---: | ---: | --- |
| D1 | 1461 steps, 80.01% | 181 steps, 9.91% | 184 steps, 10.08% | fixed paper dates when available |
| D2 | 1443 steps, 80.26% | 176 steps, 9.79% | 179 steps, 9.96% | chronological paper step counts |
| D3 | 577 steps, 61.25% | 184 steps, 19.53% | 181 steps, 19.21% | chronological paper step counts |

D1 has explicit source date boundaries:

| Source split | Date range |
| --- | --- |
| train | 2013-01-01 to 2016-12-31 |
| validation | 2017-01-01 to 2017-06-30 |
| test | 2017-07-01 to 2017-12-31 |

For D4-D6, phase 1 must encode source split as an explicit dataset-config value because the paper tables do not define those extended datasets. The extension protocol is derived from the target test horizon:

1. Confirm the target test window length for the dataset. The default is approximately 6 months, represented as 180 daily steps unless the dataset calendar requires an exact date/step count.
2. Set source test to the same horizon length as target test. When calendar dates are available, align source test to the target test date range; otherwise use the final `target_test_steps` observations.
3. Set source validation to the immediately preceding horizon of the same length.
4. Assign all earlier source history to source train.

This means D4-D6 source entities still use long-history training: only the final two horizons are reserved for validation and test, and the remaining earlier history is used for source train. The smoke report must record the resolved target test length, source validation length, source test length, source train length, and whether the split used calendar dates or step counts. This default is an extension protocol, not a claim of paper reproduction.

| Dataset | Target test | Source validation | Source test | Source train |
| --- | --- | --- | --- | --- |
| D4 | approximately 6 months, default 180 daily steps | preceding same-length horizon | same length as target test, aligned when possible | all earlier source history |
| D5 | approximately 6 months, default 180 daily steps | preceding same-length horizon | same length as target test, aligned when possible | all earlier source history |
| D6 | approximately 6 months, default 180 daily steps | preceding same-length horizon | same length as target test, aligned when possible | all earlier source history |

KNN source selection uses a third, separate window:

```python
{
    "target_observed_days": 30,
    "source_candidate_aligned_days": 30,
    "alignment": "same_relative_or_calendar_period_as_target_observed_window",
}
```

KNN compares the target domain's first 30 observable days against each source candidate's aligned 30-day sales pattern. It does not use the full source train/validation/test windows for distance calculation.

Dataset-specific domain and forbidden columns:

| Dataset | `domain_col` | `domain_col_fallback` | `forbidden_feature_cols` |
| --- | --- | --- | --- |
| D1 | `entity_id` | `error` | `entity_id`, `item_id`, `series_id` |
| D2 | `entity_id` | `error` | `entity_id`, `item_id`, `series_id`, `entity_id_code`, `brand_code` |
| D3 | `region_id` | `full_pool` | `entity_id`, `item_id`, `series_id`, `store_id`, `region_id`, `region_code`, `store_code` |
| D4 | `city_id` | `error` | `city_id`, `store_id`, `product_id`, `series_id` |
| D5 | `item_family` | `error` | `store_nbr`, `item_nbr`, `series_id` |
| D6 | `dept_id` | `error` | `item_id`, `store_id`, `series_id`, `d_index`, `wm_yr_wk` |

If `domain_col` is a list in later ablations, phase 1 should not automatically expand experiments. It should validate each listed domain independently and report which domain was used.

## Schema Validation

Add `apply_dataset_schema(raw_df, dataset_config)` or equivalent.

Responsibilities:

1. Verify required columns exist: configured `date_col`, `target_col`, `series_id_col`, and `is_target_entity`.
2. Verify those required columns are not entirely null.
3. Verify `sales` is numeric and non-negative.
4. Verify `is_target_entity` contains only `0/1` values.
5. Verify `forbidden_feature_cols` do not appear in:
   - `dynamic_feature_cols`
   - `static_feature_cols`
   - `knn_candidate_cols`
   - `rfe_candidate_cols`
6. Return the DataFrame unchanged except for safe dtype normalization that is explicitly documented.

Schema validation should not clean or infer missing data. Preprocessing owns cleaning; schema validation owns contract enforcement.

## Source/Target Split Contract

Add a configuration-driven branch for phase 1 smoke tests:

1. Source rows are `is_target_entity == 0`.
2. Target rows are `is_target_entity == 1`.
3. Split is per `series_id`.
4. Source entities are split using the dataset's configured long-history source protocol.
5. D1-D3 source splits must match the paper Table 3 step counts, and D1 should match the explicit Table 2 date ranges when those dates exist in the artifact.
6. D4-D6 source splits must follow the extension protocol: confirm target test horizon, reserve the same-length source test window, reserve the immediately preceding same-length source validation window, and assign all earlier source history to source train.
7. Target entities must have at least `target_train_days + target_val_days + target_test_days = 210` days.
8. Target rows are split chronologically as first 15 days train, next 15 days validation, and following 180 days test.
9. D6 target entities must have exactly the 210-day target protocol window after offline truncation unless missing-calendar days are explicitly reported.
10. KNN matching uses only the target observed 30-day window and the aligned 30-day source candidate window.
11. Empty source or target pools are hard failures.
12. Any dropped entity counts must be reported.

D1-D3 strict existing split logic may remain for formal legacy runs. Phase 1 smoke tests should exercise the new config-driven split so D1-D6 share one contract.

## Information Sharing Contract

Use `domain_col` from dataset config.

Scenarios:

- `with-sharing`: keep the full source pool.
- `without-sharing`: keep source rows whose `domain_col` value matches the target domain value.

Rules:

1. If multiple target domain values exist in a smoke sample, the filter uses the union of matching source domains and reports the values.
2. If no source rows match:
   - `domain_col_fallback="full_pool"`: use the full source pool and emit a warning.
   - `domain_col_fallback="error"`: fail the smoke test.
3. Domain columns are metadata columns and must not enter KNN/RFE when listed in `forbidden_feature_cols`.

D3 is the only phase-1 dataset expected to use `full_pool` fallback because local Rossmann data lacks true region metadata.

## KNN Forbidden-Column Contract

KNN candidate selection must exclude:

- all configured `forbidden_feature_cols`
- exact identifier columns: `id`, `date`, `entity_id`, `item_id`, `series_id`
- columns ending in `_id` when they identify entities, stores, items, products, cities, regions, states, departments, or time buckets
- columns ending in `_code`
- leakage-like columns containing:
  - `future`
  - `label`
  - `target`
  - `leak`
  - `pred`
  - `prediction`
  - `y_true`
  - `y_pred`
  - `next`

The smoke test must assert these known columns never enter KNN:

- `brand_code`
- `entity_id_code`
- `region_code`
- `store_code`
- `item_code`
- `series_id`
- `store_id`

For D4-D6, the test must also assert dataset-specific raw IDs are excluded.

## RFE Forbidden-Column Contract

RFE candidate selection must exclude the same forbidden set as KNN.

Additionally:

- `sales` is the supervised target and must not be an RFE candidate.
- `sales` may be added back after RFE only as historical input when the existing model path explicitly enables that behavior.
- `rfe_always_keep_cols` can include `sales`, but this does not mean `sales` is scored by RFE.

The smoke test must verify:

1. RFE candidate input excludes forbidden columns.
2. RFE selected output excludes forbidden columns.
3. If `sales` appears in final model features, the report marks it as `history_input`, not `rfe_selected`.

## Smoke-Test Acceptance Standard

Create a D1-D6 smoke test script or pytest suite that runs in under five minutes by default.

For each dataset:

1. Load the preprocessed artifact.
2. Load dataset config.
3. Run schema validation.
4. Build source/target split.
5. Run `without-sharing` information sharing filter.
6. Run `with-sharing` information sharing filter.
7. Run KNN on at most 50 source entities and 1 target entity, using only the target observed 30-day window and the aligned 30-day source window.
8. Run RFE candidate filtering on a small sample.
9. Verify SMAPE function returns a value in `[0, 200]` on a tiny synthetic or sampled prediction vector.
10. Write a smoke report row with pass/fail state and failure reason.

D1-D3 extra acceptance:

- Compare preprocessed artifact against the existing loader on the same sampled rows.
- `sales` mean drift must be below `0.01%`.

D6 extra acceptance:

- Read `d6_coldstart_target_ids.csv`.
- Verify all listed IDs are `is_target_entity == 1`.
- Verify no unlisted ID is marked as target.
- Verify target entities have exactly 210 days after truncation unless missing-calendar days are explicitly reported.

Smoke report outputs:

- `outputs/smoke_tests/d1_d6_smoke_report.csv`
- `outputs/smoke_tests/d1_d6_smoke_report.md`

The report must include:

- dataset name
- artifact path
- row count
- series count
- target series count
- source series count
- split status
- source split protocol status
- target `15/15/180` split status
- KNN 30-day matching-window status
- without-sharing source count
- with-sharing source count
- KNN forbidden-column status
- RFE forbidden-column status
- SMAPE status
- overall status
- failure reason

## Testing Strategy

Unit tests:

- dataset config validation rejects missing required fields.
- schema validation rejects missing required columns.
- schema validation rejects forbidden feature conflicts.
- forbidden-column helper rejects `_code`, `series_id`, known raw IDs, and leakage-like names.
- information sharing fallback behaves as configured.
- D6 target ID consistency check detects mismatch.

Smoke tests:

- one sampled path per dataset.
- max 50 source entities and 1 target entity.
- no formal training runner invocation.

Regression tests:

- D1-D3 artifact vs loader `sales` drift below `0.01%`.
- Existing strict D1-D3 tests continue to pass.

## Open Decisions For Review

1. Whether D1-D3 preprocessed artifacts should also include legacy `entity_id/item_id` columns for all rows. Recommendation: yes, to minimize phase-1 churn.
2. Whether `dataset_config` should be a new `dataset_config.py` module or integrated into `dataset_registry.py`. Recommendation: new `dataset_config.py`, with registry delegating to it where needed.
3. Whether phase-1 smoke tests should generate missing preprocessing artifacts automatically or fail with instructions. Recommendation: generate only when an explicit `--generate-preprocessed` flag is provided; otherwise fail clearly.
4. Whether D4 `domain_col` should remain only `city_id` in phase 1. Recommendation: yes; category-domain ablations should wait until phase 2.
